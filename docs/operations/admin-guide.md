# 管理员使用手册

## 1. 首位管理员与成员

首次迁移和种子完成后，在服务器容器中运行 `npm run bootstrap-admin -w @douyin/domain` 所对应的发布命令，根据提示提供工作区、邮箱、显示名和强密码。命令受数据库锁保护且只允许成功创建一次首位管理员。

后续成员只通过“成员与邀请”加入，没有公开注册。邀请有有效期且只能使用一次。角色边界：

- 管理员：成员、邀请、设备、模板、审计和全部运营操作。
- 运营人员：任务、运行、复核与合作跟进，不能管理系统密钥。
- 只读成员：查看授权业务数据，不能修改。

成员离职或账号异常时立即停用账号并撤销全部会话；在审计记录中确认动作已留痕。

## 2. 设备生命周期

在“采集设备”生成短期一次性配对码，交给指定同事当面或通过受控渠道输入。设备令牌只在配对时显示一次，服务端只保存哈希，本机由 Windows DPAPI 保护。

设备丢失或换人时先撤销；怀疑令牌泄露时执行轮换并重新配对。撤销后旧令牌不能继续查看运行或提交批次。服务器永远不能代替运营同事点击“人工开始”。

## 3. 安全检查

- 每月复核成员、角色、活跃会话和已配对设备。
- 每周查看审计中的账户、规则、设备、复核、合作和导出动作。
- RDS 只允许服务器出口 IP `/32`，业务账号与迁移账号分离并强制 TLS。
- OSS bucket 保持 private，RAM 权限限定 bucket/prefix；只签发短期 PUT/GET。
- 对外仅开放 80/443；不要开放 API、worker、MySQL 或容器管理端口。
- 日志和导出中不得出现 Cookie、Authorization、设备令牌、密码或 OSS key。

## 4. 入库闸门与证据回收

### 入库闸门

只有全部硬筛规则都判“通过”的达人才会创建候选行。判“不通过”或“未知”的达人只留在不可变的观察记录里，不进入复核队列，采集助手也不再为其截图上传。因此达人库条目数会明显少于运行监控里的“已核验作者数”，这是预期行为，不是采集故障。

界面上没有按硬筛结论筛选的入口（分区轴已改为合作阶段），但服务端过滤仍然保留：`GET /candidates` 与 `GET /exports/candidates.csv` 都接受 `hardFilterStatus`，取值 `pass`、`fail`、`unknown`。它的用途是检索闸门上线前遗留的存量 `fail` / `unknown` 候选行；闸门之后新建的行只会是 `pass`。该参数与其余查询条件一样受工作区和角色鉴权约束，不能用来越权读取数据。

未入库达人的结论与判定依据在“运行监控”选中运行后的“本次运行观察到的达人”面板查看，由采集事实与该运行保存的规则快照重新推导。运营人员问“为什么没入库”时指向该面板。不要往 `campaign_candidates` 手工补行：补出来的行没有对应的硬筛通过事实，会污染复核队列、负责人分配和后续统计。

### 孤儿证据回收

worker 每 `MEDIA_CLEANUP_INTERVAL_MS`（默认 1 小时）跑一轮素材清理，单轮每条路径最多处理 `MEDIA_CLEANUP_BATCH_SIZE` 条（默认 100，上限 500），按时间从最老开始，因此积压会分多轮排空而不是一次删穿整张表。三条路径互不重叠：

| 路径 | 判据 | 计数字段 |
| --- | --- | --- |
| 未确认回收 | `pending` 且签名地址已过期，或已被 claim 为 `expired` | `deletedUnconfirmed` |
| 超期留存回收 | `confirmed` 且确认时间超过 `MEDIA_RETENTION_DAYS`（默认 180 天），且所属任务已归档或不存在 | `deletedConfirmed` |
| 孤儿回收 | `confirmed` 且确认时间超过 `ORPHAN_MEDIA_GRACE_DAYS`，且该达人在本工作区没有任何候选行 | `deletedOrphans` |

新增的两个变量：

- `ORPHAN_MEDIA_CLEANUP_ENABLED`：默认 `false`，只接受 `true/false/1/0`，其他值会被在线预检拦下。
- `ORPHAN_MEDIA_GRACE_DAYS`：默认 `7`，范围 1–3650 的整数天。

**孤儿回收是三条路径里风险最高的一条，因此默认关闭。** 前两条要么针对从未确认成功的临时对象，要么要求任务已归档且证据已满 180 天；孤儿回收却会在任务仍然活跃、证据只有 7 天大小时删除已确认的截图，判据只有“没有候选行引用”这一条。OSS 对象删除后不可恢复，而对应的达人主页也无法重新采集。

开启前确认：

1. 入库闸门工作正常。闸门若因规则快照或版本问题漏建候选行，正常达人的截图会被误判为孤儿。
2. 宽限期长于“素材确认 → 候选行建立”的最大正常间隔。正常情况下两步在同一次同步里几乎同时发生，7 天已经很宽裕；只有在排查过历史数据后才考虑调小，不要凭直觉调成 1 天。

判据本身还有两条保守约束，排查时可以依赖：素材必须能通过 `creator_observation_id` 关联到真实的达人观察记录（`creator_observation_id` 为空或只关联作品观察的素材一律不回收），且判定的粒度是达人而非单条观察 —— 只要该达人在本工作区有任意一条候选行，他名下所有素材都会被保留。

成功日志形如 `{"event":"media.cleanup.completed","deletedConfirmed":0,"deletedOrphans":0,"deletedUnconfirmed":0,"failed":0,"preservedReferenced":0}`，五个字段都是纯数字计数，不含 bucket 名、object key 或任何永久地址。`preservedReferenced` 是本轮超过留存期的已确认素材总数减去实际选中删除的条数，因此既包含因任务仍活跃而保留的，也包含因批量上限留到下一轮的；它只统计留存路径，不反映孤儿路径。失败收敛为 `{"event":"media.cleanup.failed","errorType":"..."}`，只记错误类型，不阻塞后续轮次，也不影响其他后台任务。

删除分三步执行：先把行 claim 为 `expired`，再删 OSS 对象，最后标记 `deleted`。中途失败的对象停留在 `expired`，由下一轮的未确认路径补删；孤儿路径只取 `confirmed` 行，因此不会重复 claim 同一个对象。

建议的上线顺序：先只部署代码、保持开关关闭，观察一轮确认五个计数符合预期，再显式开启。

## 5. 管理交接

交接时只移交凭据所在的密码管理器条目和操作文档，不复制浏览器画像。至少两名管理员掌握部署回滚与账户停用流程；每次权限或密钥变更记录日期、执行人、原因和审计事件 ID。
