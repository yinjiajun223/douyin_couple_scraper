## Context

现有 `CollectorRuntime` 长期复用一个推荐流页和一个作者核验页。每次作者页导航完成后，`safety-gate.ts` 只根据 URL、标题和正文正则分类；「服务异常」「网络错误」「请求异常」「访问频繁」「账号异常」以及 HTTP 4xx/5xx 被合并成 `abnormal_page`。`runtime.ts` 收到任何该类问题都会抛出 `CollectionPausedError`，保存检查点并把远端运行改为 `paused`，没有自动恢复阶段。

本机 v0.1.5 检查点证明同一失败至少发生两次：约 45 分钟 / 382 位作者和约 79 分钟 / 656 位作者；约 11 分钟 / 96 位作者的运行正常完成。用户关闭整个浏览器后可以继续。该证据确认了「暂时性或长期浏览器状态故障被直接判成不可恢复暂停」，但当前检查点没有主文档响应状态、请求失败代码、恢复阶段或浏览器代际，因此还不能证明外部触发一定是抖音风控。

现有规则契约已接受 `maxDurationMinutes` 1–1,440，运行进度与批次也已有本地检查点、幂等键和断网重试，因此 24 小时能力不需要新协议或数据库迁移。主要缺口是故障分类、浏览器生命周期恢复、可取消退避、脱敏诊断和真实长运行验证。`tighten-review-funnel` 已在源码中收紧截图上传门控，但尚未发布新采集器；本变更的下一次自然发包会同时带上该既有源码改动。

## Goals / Non-Goals

**Goals:**

- 对单独出现的服务异常、网络错误、请求异常和瞬时服务端故障执行低频、有界、可取消的自愈，而不是第一次命中即暂停。
- 对登录失效、验证码、安全验证、访问频繁、账号异常和无法可靠分类的情况继续 fail-closed。
- 在恢复中保留当前运行、当前作者和本地批次的幂等语义，恢复成功后不重复计数、同步或上传。
- 让一次人工启动的运行在电脑和进程保持工作的前提下，可稳定执行到最长 1,440 分钟的停止条件。
- 留下足以区分「刷新即恢复」「重建页面才恢复」「重启上下文才恢复」「始终不恢复」的脱敏证据。

**Non-Goals:**

- 不尝试逆向或绕过抖音验证码、账号限制、访问频繁策略或其他安全机制。
- 不承诺任何账号、网络或平台状态下都能连续发出请求 24 小时；退避、冷却和安全暂停属于正确行为。
- 不由服务端远程启动浏览器，不自动领取、创建或启动下一次运行。
- 不在本变更中增加 Windows 开机自启、系统防休眠、进程守护或崩溃后无人确认的自动续跑。
- 不在缺少网络证据时把外部触发武断定性为硬风控；先通过本变更的诊断记录收集可验证信号。

## Decisions

### D1: 将安全结果拆为人工事件、暂时性故障和解析质量问题

`safety-gate.ts` 不再用一个 `abnormal_page` 覆盖所有异常。分类优先级固定为：

1. `login_required` / `captcha_required` / `platform_restriction`：URL、正文或响应证据命中登录、安全验证、验证码、访问频繁、账号异常、HTTP 401/403/429 等明确限制时立即暂停。
2. `transient_page_failure`：只命中服务异常、网络错误、请求异常、主文档 5xx、导航超时或连接中断，且不存在上一类信号时进入恢复。
3. `low_parser_confidence`：页面通过安全检查后，解析字段仍低于可信度阈值时沿用既有跳过/暂停策略。

无法可靠分类时保持 fail-closed。安全事件必须先于暂时性故障判断，避免同时出现验证码文案和服务异常文案时误入自动恢复。

备选方案是继续把所有异常立即暂停；它最保守，但正是本次长运行中断的直接原因。另一备选是所有异常都自动刷新；它可能对验证码或平台限制持续施压，不符合项目边界。

### D2: 在解析作者数据前完成页面安全取证

作者页导航需要同时取得主文档状态、导航失败类型、当前 URL、标题和正文的安全分类结果。先完成安全分类，再调用平台解析器；否则错误页可能先触发身份不匹配或低可信度，丢失真正的「服务异常」信号。

页面取证只保留分类所需的瞬时值。持久诊断不得写入正文、标题、完整 URL、响应头或响应体；只落盘页面类型、分类代码、HTTP 状态或白名单化的导航错误代码。

备选方案是在现有解析完成后继续调用 `findSafetyIssue`；这无法覆盖解析器先抛错的错误页，也无法稳定区分 HTTP 5xx 与页面结构变化。

### D3: 使用低频、三级、同作者恢复阶梯

暂时性故障发生时，助手先保存检查点，并针对尚未确认的同一作者按以下阶段恢复：

1. 等待约 15 秒并带随机抖动，重新加载或重新导航当前页面。
2. 若仍失败，等待约 60 秒，关闭并重建作者核验页，再导航同一作者。
3. 若仍失败，等待约 5 分钟，关闭当前浏览器上下文并用同一个持久画像重新启动可见 Chrome，重新建立推荐页与作者页后再尝试。

每个阶段只执行一次；完整上下文重启后仍失败即暂停。同一类故障恢复后 2 分钟内再次出现视为同一事件，直接进入下一阶段；滚动 60 分钟内发生 3 次完整上下文恢复则触发熔断并暂停。上述数字先作为代码常量，不增加普通用户配置，避免把安全预算变成容易误配的界面参数；真实试运行后只能在保持规格边界的前提下调优。

明确访问频繁、账号异常、登录和验证码不进入该阶梯。相比立即重启浏览器，先等待和页面级恢复能降低额外请求压力；相比无限重试，恢复预算和熔断给平台限制保留 fail-closed 边界。

### D4: 浏览器上下文使用代际管理，区分内部重启与人工关闭

当前 `context.once('close')` 无条件把 `stopped` 设为 `true`，因此不能直接复用于自动重启。运行时应为每次上下文分配代际，并通过明确的内部关闭原因执行替换：只有当前代际的非计划关闭才视为用户关闭浏览器并暂停；恢复流程计划关闭旧代际时不得把运行停止。

任一时刻最多存在一个浏览器上下文、一个推荐页和一个作者核验页。上下文替换后清空只属于旧推荐页的内存 feed 缓存，再用同一持久画像打开抖音首页；不得复制、导出或修改 Cookie。恢复完成前不处理下一个作者。

不采用定时强制重启浏览器：目前没有证据证明固定时长是根因，主动重启会干扰推荐流并产生额外平台访问。先做故障驱动恢复，使用诊断结果决定以后是否需要周期性回收。

### D5: 恢复等待必须可取消，检查点与幂等边界保持不变

退避不能直接使用一次性 5 分钟睡眠，否则人工暂停会被阻塞。运行时增加可取消等待原语；暂停、终止、浏览器被人工关闭或远端状态不再是 `running` 时立即退出后续恢复。

发生故障的作者在取得可信解析前不得加入 `seenCreators` / `seenPosts`，也不得递增进度。已有 `pendingBatch` 仍优先完成同步；自动恢复不改变批次 idempotency key。恢复耗时计入 `elapsedSeconds`，因此 24 小时停止条件在退避期间仍然有效。

### D6: 用兼容旧检查点的恢复状态和有界本地事件日志留证

检查点增加可选 `recovery` 字段，旧版检查点缺失时归一化为 idle。字段包括安全分类、页面类型、阶段、尝试次数、事件开始时间、下次尝试时间、最近结果和滚动熔断计数，不包含目标主页地址。

另写本机有界 JSONL 恢复日志，单文件最大 1 MiB、最多保留 3 个轮转文件。允许字段限定为时间、运行 ID、采集进度计数、页面类型、分类代码、HTTP 状态或白名单化导航错误、恢复阶段、浏览器代际和结果；严禁正文、标题、完整 URL、请求/响应头、Cookie、Authorization、设备令牌或截图。控制页只展示当前或最近一次恢复摘要。

仅写检查点的备选方案不足以分析多次故障；无限日志又会给 24 小时运行带来磁盘增长风险，因此选择小型轮转日志。

### D7: 复用现有 1,440 分钟规则，不新增持续运行协议

`packages/contracts` 已把最长运行时间限定为 1–1,440 分钟，服务端按 `elapsedSeconds` 判停；无需 schema version、API 或数据库迁移。网页表单补 `max=1440` 和说明：若希望按时间跑满 24 小时，应清空会更早触发的作品数、作者数或候选数条件，因为多个停止条件是 OR 关系。

长运行仍由运营人员在本机点击开始。完成、终止、进程退出或电脑休眠后不会自动启动另一运行。自动恢复只维持这次已授权运行，不扩大远程控制边界。

### D8: 以运行级故障注入作为回归主信号

在现有 `runtime-settings.test.ts` 的真实运行循环 mock 层构造与截图相同的「服务异常」：第一次作者页失败，随后分别在刷新、重建页面和重建上下文阶段恢复。测试必须先证明当前实现会把远端运行改为暂停，再在修复后证明同一作者被继续处理、批次只发送一次、进度只递增一次。

另覆盖验证码/访问频繁立即暂停、恢复预算耗尽、人工暂停取消退避、旧检查点兼容、浏览器页数有界、日志脱敏与轮转，以及用假时钟加速的 24 小时稳定性用例。真实抖音只能用于小范围验收，不能替代确定性的故障注入回归测试。

## Risks / Trade-offs

- [「服务异常」实际是未显式标记的软风控] → 先长退避、限制三级恢复和滚动熔断；若恢复后短时间复发则暂停，不循环重启规避限制。
- [浏览器上下文重启影响推荐流位置] → 复用同一持久画像与本地已见集合；允许重新看到旧内容但不得重复写入，恢复后由推荐流重新定位新内容。
- [恢复时当前作者无法再次定位] → 恢复状态机在当前进程内保留待核验项并完成同作者恢复；若进程退出则沿用既有人工继续语义，由推荐流重新发现，诊断日志不新增完整地址。
- [24 小时运行导致检查点和内存集合增长] → 保留现有 10,000 作品 / 2,000 作者规则上限，增加加速 soak 测试和文件大小断言；日志单独轮转。
- [人工暂停在页面导航或关闭上下文期间发生竞态] → 所有恢复步骤检查同一个停止信号和浏览器代际，结束时以人工动作和服务端状态为准。
- [新版采集器同时包含未发布的截图门控改动] → 发布验收同时回归 pass 才上传截图、fail/unknown 仍同步结构化观察，避免把两个变更的异常混淆。
- [未执行真实长时间专项试跑] → 用户于 2026-09-23 确认取消两小时和 24 小时专项验收，改为本人线上使用验收、发现问题后修复；保留自动化回归、包级冒烟和已完成的小规模试跑证据，不将取消项目记为测试通过或宣称真实 24 小时稳定性已验证。

## Migration Plan

1. 先落故障分类、运行级失败测试和脱敏诊断，不改变生产默认启动方式；确认现有验证码、登录和平台限制测试仍为立即暂停。
2. 实现可取消恢复状态机、浏览器代际替换、检查点兼容与控制页展示，运行 collector 定向测试、全仓检查、MySQL/E2E 回归和 Windows 包冒烟。
3. 网页表单补 1,440 分钟上限提示并随正常 web 发布；API、数据库和采集协议无需迁移。
4. 构建下一版 Windows 采集器，在同级新目录解压并复用 `../data`；保留 v0.1.5 目录和校验值作为回退。macOS 包仍按既有规则在两种架构真机验证后再宣布可用。
5. 保留受控故障验收和小规模真实试跑。用户已确认小规模运行正常完成：浏览 100 条作品、核验 96 位作者、1 位硬筛通过、0 次解析跳过。按用户于 2026-09-23 确认的调整，不再安排至少两小时 canary 和 24 小时专项真实运行，也不再将两项作为发布前置门槛；由用户在线上日常使用中验收，发现问题后再修复。
6. 线上反馈出现异常时，依据脱敏日志、运行状态和用户提供的页面证据排查故障类别、恢复阶段及暂停原因，不预先把外部原因归为硬风控。取消专项试跑不改变 1,440 分钟运行能力、自动恢复预算或人工安全暂停边界，也不代表长时间稳定性已通过真实验证。后续发布时同步发布说明中的验收门槛，其他发布与回退验证待办保持不变。

回滚采集器时先暂停当前运行，关闭新版浏览器，从保留的 v0.1.5 目录启动并继续同一检查点；不删除共享 `data`。网页提示可独立回滚。新版未提高 `COLLECTOR_MIN_VERSION`，因此旧包仍受服务端接受。

## Open Questions

- 用户线上使用中最早成功的恢复阶段是刷新、重建作者页还是完整上下文重启？收到实际反馈后评估是否需要调整阶段顺序，但不改变有界恢复规格。
- 用户线上长时间使用的实际故障频率是否需要把默认访问节奏进一步放慢？收到反馈后用脱敏事件和候选产出率评估，不另行安排专项试跑；任何调整仍须保持低速、人工启动和安全熔断边界。
