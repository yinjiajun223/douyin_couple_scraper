## Why

当前项目只能通过固定关键词搜索抖音情侣账号，并以粉丝数生成本地 CSV 和截图，无法支持运营团队从已养好的推荐流中持续发现不同圈层的素人博主，也无法在保证成员数据隔离的前提下集中管理候选、复核结论和合作进度。需要将它升级为以“可配置筛选任务”为核心的团队达人运营平台，同时保留人工控制抖音推荐画像和最终判断。

## What Changes

- 建立部署在现有 Ubuntu 服务器上的内部 Web 管理后台与 API，使用 MySQL 8.0 持久化业务数据、使用私有阿里云 OSS 保存截图与分析素材。
- 建立仅限内部邀请的账户体系，提供管理员、运营人员和只读成员权限，并记录关键业务操作。
- 将筛选条件从脚本常量改为任务级配置，区分可确定的硬筛规则、AI 辅助规则和人工复核项；首个默认模板为粉丝 0-5000、近 15 天至少一条作品点赞达到 10000、疑似年龄 18-24 岁、素人账号、内容类型不限。
- 将候选发现入口由固定关键词搜索扩展为抖音推荐流采集。运营人员在各自电脑上人工养号，本地采集助手使用独立持久浏览器资料低速读取推荐作品和作者，不自动点赞、关注、评论、私信或点击“不感兴趣”。
- 建立统一去重但按成员归属隔离的达人与作品库：管理员可以查看全部数据，运营人员和只读成员只能查看自己设备采集或被分配给自己的达人；保留每次采集快照、命中规则的作品证据、来源任务和去重结果，并按首次发现日期分类和分页；未知数据不得按 0 处理。
- 在硬筛之后接入可配置的外部多模态 AI，对公开截图、简介和文案进行年龄段、素人属性、内容方向、推广适配度与风险的辅助判断，并返回依据与可信度；AI 不可用时核心流程仍可运行。
- 提供人工复核及轻量合作跟进，支持待复核、不符合、待联系、已联系、沟通中、已合作和不合作等状态以及备注、联系方式、报价和操作历史。
- 第一版只实现抖音，预留平台适配边界供后续接入小红书、快手等平台。

## Capabilities

### New Capabilities

- `internal-access-control`: 内部邀请制账户、角色权限、设备授权和关键操作审计。
- `screening-campaigns`: 可复用的筛选任务、硬筛规则、AI 规则、人工复核项与默认任务模板。
- `douyin-local-collection`: 由运营电脑运行的抖音推荐流采集助手、持久登录资料、人工介入和安全同步边界。
- `creator-candidate-library`: 统一达人主档、按成员归属隔离的候选视图、作品与采集快照、规则证据、日期分类、分页、去重和素材引用。
- `ai-assisted-screening`: 可切换供应商的多模态 AI 连接、硬筛后分析、结构化结果、可信度、成本边界和失败降级。
- `creator-review-and-outreach`: 人工复核、合作跟进状态、业务字段、历史记录和数据导出。
- `hosted-platform-operations`: Ubuntu 服务器部署、MySQL 8.0、私有 OSS、后台任务、健康检查和安全配置。

### Modified Capabilities

无。当前仓库尚无已建立的 OpenSpec 能力规格。

## Impact

- 当前单文件 Node.js/Playwright 脚本将演进为服务器端管理应用、API/后台任务和 Windows 本地采集助手三个协作部分。
- 需要新增 Web 前端、账户与权限、MySQL 数据模型及迁移、OSS 签名上传、外部 AI 适配器、设备令牌和同步 API。
- 现有持久浏览器资料、粉丝数字解析、公开主页读取和限速思路可被本地采集助手复用；固定情侣关键词、固定粉丝范围和本地静态 HTML 不再作为主要业务入口。
- 部署依赖现有 Ubuntu 主机、域名、MySQL 8.0 RDS 和阿里云 OSS；若 ECS 与 RDS 同地域同 VPC，生产部署应优先使用 RDS 内网连接。
- 第一版不包含其他内容平台、自动养号、自动互动、自动私信、完整视频上传或以 AI 结论自动淘汰候选人。
